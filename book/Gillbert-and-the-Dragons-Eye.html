Hendricks, four seconds later

It is not a blender. A blender destroys structure. A compiler preserves structure and throws away names.

Your loop is still a loop after compiling. Your if is still a branch. Your comparison is still a comparison, in the same order, with the same constant. What you lose is the labels: variable names, function names, comments, types. The skeleton survives perfectly. Only the name tags come off.

Reverse engineering is the craft of putting the name tags back on.

Chapter 0.1

Your Chromebook is two computers

And you have only ever been allowed to use one of them.

A Chromebook looks like a machine that runs a browser and nothing else. For years that was basically true. It is not true anymore.

Underneath ChromeOS there is a feature called the Linux development environment. Turn it on and ChromeOS quietly boots a small, real, complete Debian Linux machine in a container next to your browser. It has its own file system, its own package manager, and its own terminal. Programs you run inside it cannot wander out and break ChromeOS, which is exactly the property you want when you are running twelve programs written by a villain.

Why this matters for what we are doing

Ghidra is a desktop application written in Java. It cannot run in a browser tab. Neither can gdb, or ltrace, or the mission binaries themselves, which are Linux executables.

So the Linux environment is not a nice-to-have here. It is the lab. Everything in this book happens inside it.

The one thing that can stop you

If your Chromebook is managed by a school or an organisation, an administrator can switch the Linux environment off for the whole fleet. If that has happened, the option will be missing from Settings entirely, or it will be there but greyed out with a little building icon next to it.

That is not something you can work around, and you should not try. Go and read the box in Chapter 0.8 called "If Linux is not there at all", which has three real alternatives, one of which is very good.

Chapter 0.5

Installing Java 21

Ghidra is written in Java and it is fussy about the version.

Ghidra needs a 64-bit JDK, version 21 or newer. Not a JRE, a JDK. Not version 17. Getting this wrong is the single most common reason Ghidra refuses to start, so let us just do it properly.

Try the easy way first:

$ sudo apt install -y openjdk-21-jdk

If that worked, skip to the check at the bottom of this page. If it said Unable to locate package, your Debian is a version whose main catalogue stops at Java 17. Add the backports catalogue and try again:

$ cat /etc/debian_version        # tells you which Debian you have
12.11

# for Debian 12 ("bookworm"):
$ echo "deb http://deb.debian.org/debian bookworm-backports main" \
      | sudo tee /etc/apt/sources.list.d/backports.list
$ sudo apt update
$ sudo apt install -y -t bookworm-backports openjdk-21-jdk
What backports means

Debian's stable release freezes package versions for years on purpose, because "boring and predictable" is a feature for servers. Backports is an official extra catalogue holding newer versions of some packages, rebuilt for that stable release. It is run by Debian. It is not a shady third-party source.

If cat /etc/debian_version gave you 13 or higher, the word bookworm above should be trixie, and you very likely did not need backports at all.

Check it

$ java -version
openjdk version "21.0.x" 2025-xx-xx
OpenJDK Runtime Environment (build 21.0.x+xx-Debian-...)
OpenJDK 64-Bit Server VM (build 21.0.x+xx-Debian-..., mixed mode)

Two things must be true: the version starts with 21 or higher, and the third line says 64-Bit. If both are true, you are done here.

If java -version still says 17

You have two Javas installed and the old one is winning. Fix it with:

sudo update-alternatives --config java

It prints a numbered list. Type the number next to the java-21 entry and press Enter.

Chapter 0.6

Installing Ghidra

No installer. You unzip it and it is installed. That is the whole process.

Ghidra does not have a setup program. It is a folder. You download the zip, unpack it, and run the launcher from inside. To uninstall it, you delete the folder. Refreshingly blunt.

Download it from inside Linux

Ghidra's releases live on GitHub. This one-liner asks GitHub which release is newest and downloads it, so you never have to type a version number:

$ cd ~
$ URL=$(curl -s https://api.github.com/repos/NationalSecurityAgency/ghidra/releases/latest \
        | grep browser_download_url | grep PUBLIC | cut -d'"' -f4)
$ echo "$URL"
https://github.com/NationalSecurityAgency/ghidra/releases/download/Ghidra_12.1.3_build/ghidra_12.1.3_PUBLIC_20260xxx.zip
$ wget "$URL"

It is around 400 MB. Now unpack it:

$ unzip -q ghidra_*_PUBLIC_*.zip
$ ls -d ghidra_*/
ghidra_12.1.3_PUBLIC/
Or do it in the browser

If you would rather see what you are downloading: open Chrome, go to github.com/NationalSecurityAgency/ghidra/releases, and click the ghidra_..._PUBLIC_....zip file at the top of the newest release. It lands in your ChromeOS Downloads folder. Chapter 0.7 explains how to get it from there into Linux.

Start the dragon

$ cd ~/ghidra_*_PUBLIC
$ ./ghidraRun

The first launch takes a while and prints a wall of text you can ignore. Then a splash screen appears, then a mostly empty window with a menu bar. That empty window is correct. Ghidra opens with no project, the same way a word processor opens with no document.

Why ./ghidraRun and not just ghidraRun

When you type a bare command name, Linux searches a specific list of folders for it, and the folder you are standing in is deliberately not on that list. That is a security decision from the 1970s that turned out to be correct: it means dropping a file called ls into a folder cannot trick someone into running it.

./ means "the folder I am standing in, and I mean it." You will type it in front of every mission binary too.

Make it easy to launch later

$ echo "alias ghidra='~/ghidra_12.1.3_PUBLIC/ghidraRun'" >> ~/.bashrc
$ source ~/.bashrc

Change the version number to match what you actually downloaded. From now on typing ghidra starts it.

Chapter 1

From your code to the machine's code

What the compiler keeps, and what it throws in the bin.

In Volume One you wrote JavaScript. The browser read the actual words you typed, every time it ran. Your variable named playerHealth was still called playerHealth at three in the morning while the game was running.

C works differently. You write it, then a compiler translates the whole thing into instructions your processor understands directly, and saves those instructions into a file. From then on nobody reads your C. The processor reads the instructions.

Here is what goes in

int add_and_double(int a, int b)
{
    int total = a + b;
    return total * 2;
}

And here is what comes out

; the same function, as instructions
add     %esi, %edi        ; add b into a
lea     (%rdi,%rdi,1), %eax  ; put a+a into the answer register
ret                       ; hand it back

Look at what survived and what did not.

In your sourceAfter compiling
The name add_and_doubleSometimes kept, as a label, but easily removed
The names a, b, totalGone. They are registers now
The comment you wroteGone. Completely and forever
The additionThere. One instruction, exact
Multiplying by twoThere, but rewritten as adding the number to itself, because that is faster
The order things happen inThere, and it has to be
The one sentence that this whole book rests on

The compiler removes names and it removes intent. It cannot remove behaviour, because behaviour is the only thing it was hired to deliver.

So: you will never recover the original variable names. You will never see the comments. But you can always, always recover exactly what the program does, because the machine has to be told exactly what to do, in writing, in that file.

Notice that last row again

The compiler turned total * 2 into total + total. It did that on purpose, because addition is cheaper than multiplication and both give the same answer.

This is going to happen constantly and it is the thing that trips people up first. What you read back is not what somebody wrote. It is what somebody wrote after an extremely clever machine rearranged it for speed. Those are not the same document, and expecting them to match is the fastest way to get confused.

Dudley's analogy, which Richard has approved this time

It is like translating a poem into Japanese and then back into English. The meaning survives the round trip perfectly. The exact words do not, and anyone who insists the words must come back identical is going to have a difficult afternoon.

x86-64 The processor it is built for. If yours says ARM aarch64, you picked the ARM folder, which is correct for you.
dynamically linked It borrows common functions like printf from the system rather than carrying its own copy. This is very good news for you later, in Part 3.
not stripped The most important two words on the line. The function names are still in there.

Stripped versus not stripped

A compiled program can carry a table of function names, purely as a courtesy to humans. The processor never reads it. You can delete that table with one command and the program runs identically.

Deleting it is called stripping, and it is the single biggest thing standing between an easy afternoon and a hard one.

$ file m06_keyforge
m06_keyforge: ELF 64-bit LSB executable, x86-64, ..., stripped
Your first six missions are on easy mode and you should know it

Missions 06 to 12 are stripped. No names at all. Chapter 18 is entirely about what to do then, and it is the chapter that separates people who can do this from people who have watched a video about it.

Chapter 3

The map at the front of the program

Sections: where the code lives, where the constants live, and why it matters.

An ELF file is not a soup of bytes. It is organised into sections, each with a name and a job, and there is a table at the front listing them. Ask for it:

$ readelf -S m01_helloghost
  [Nr] Name         Type      Address           Offset
  [15] .text        PROGBITS  00000000004010d0  000010d0
  [17] .rodata      PROGBITS  0000000000402000  00002000
  [25] .data        PROGBITS  0000000000404028  00003028
  [26] .bss         NOBITS    0000000000404040  00003038

Four of those matter enormously and the rest you can ignore for now.

The four sections you care about
SectionHoldsWhy you care
.text The actual machine instructions. This is the program. Ghidra spends all its time here.
.rodata Read-only data. Every string literal you wrote, every constant table. This is where passwords hide. Almost every early mission is won here.
.data Variables that start with a value and can change while running. Sometimes a secret lives here instead, especially if the program modifies it.
.bss Variables that start at zero. Takes up no space in the file at all, just a note saying "reserve this much". Where runtime-built strings usually end up living.

Look inside .rodata directly

$ objdump -s -j .rodata m04_xorlock

 402020 53204752 414e5445 442e2053 616d6520  S GRANTED. Same
 402030 62797465 732e2044 69666665 72656e74  bytes. Different

Two columns. On the left, the raw bytes in hexadecimal. On the right, the same bytes shown as text where they happen to be readable, and as a dot where they are not.

Look at the highlighted run: f2 ea e9 e3 ed e4 e9 e0 fc, then a zero. Nine bytes and a terminator, sitting at the very start of the read-only data, right where a string literal would be, and every single byte is above 7f so it shows as dots.

That is not text. That is nine bytes that used to be text.

Hold that thought until Mission 04.

Addresses versus offsets

readelf printed two numbers for each section. Address is where the section will live in memory when the program runs. Offset is how far into the file it sits on disk. They are different numbers for the same thing and mixing them up will waste an hour of your life.

Ghidra shows you addresses. So does gdb. Stick to addresses and you will rarely need offsets at all.

Chapter 4

strings: the free lunch

Ten seconds of effort. Sometimes it just wins.

strings walks through a file looking for runs of printable characters four or more long, and prints each one. That is the entire algorithm. It is almost embarrassingly simple and it is still the first thing a professional runs on an unknown binary, every time, without fail.

$ strings m01_helloghost
/lib64/ld-linux-x86-64.so.2

A locked door. No hints. Password:
NULLYWASHERE
  ACCESS GRANTED. Nully's first door swings open.
  SHARD %02d: %c
  ACCESS DENIED. The door does not move.
...

There it is, sitting between the prompt and the success message, exactly where a password constant would end up. No cleverness required.

FlagEffect

What strings does not find, which is the actual lesson

It only finds runs of printable ASCII. It will walk straight past:

  • Anything encoded, encrypted, or XORed into non-printable bytes
  • Anything built one character at a time while the program runs
  • Anything stored as 16-bit wide characters
  • Anything shorter than four characters

Chapter 6

Strings that hide

Six ways to put text in a file where strings will not see it. Lab: lab_strings.

Run this and count what comes out:

$ chmod +x lab_strings
$ ./lab_strings
$ strings lab_strings | grep -v -E '^(_|\.|GLIBC|GCC|/lib)'

Nine things are hidden in that file. strings shows you some of them outright, shows you others in a disguise you have to recognise, and misses two entirely. Here is the field guide.

1. Plain text

CONTAINMENT CONSOLE BUILD 2026.08. Nothing to it. This is the free lunch.

2. Rotated letters

AHYYL VF ABG VA GUVF SVYR

That is English with every letter pushed thirteen places along the alphabet. It is called ROT13, it is about as strong as writing in mirror handwriting, and it is everywhere. Recognising it on sight is worth doing: the giveaway is text with correct English word lengths and spacing but nonsense letters.

$ echo "AHYYL VF ABG VA GUVF SVYR" | tr 'A-Za-z' 'N-ZA-Mn-za-m'

That one-liner decodes it. It also encodes it, because ROT13 applied twice gets you back where you started, which is either elegant or a warning sign depending on your mood.

3. Base64

dGhlIGZsYWcgaXMgbm90IGhlcmUgZWl0aGVyLCBuaWNlIHRyeQ==

Letters, digits, plus and slash, and often = padding on the end. Base64 is a way of writing arbitrary bytes using only safe characters. It is not encryption and it was never meant to be.

$ echo 'dGhlIGZsYWcgaXMgbm90IGhlcmUgZWl0aGVyLCBuaWNlIHRyeQ==' | base64 -d

4. Hex

4e4f5420415320454153592041532049542044454d4f

Only the characters 0-9 and a-f, and always an even number of them. Each pair is one byte.

$ echo '4e4f5420415320454153592041532049542044454d4f' | xxd -r -p

5. Wide strings, which strings walks straight past

Some systems store text as two bytes per character, with the second byte usually zero. To strings, W\0I\0D\0E\0 looks like a series of one-letter runs, all too short to report. So it reports nothing.

$ strings -e l lab_strings
WIDE STRINGS HIDE FROM strings

The -e l means "16-bit little-endian". If you ever get a suspiciously empty strings result on a Windows program, this is the first thing to try.

6. Masked bytes

The last one is not there in any encoding, because it is not text in the file at all. It is a block of bytes that only becomes text after the program does arithmetic on it. Run the lab: it prints FOUND IT, and that string does not appear anywhere in the file.

The pattern to take away

Every one of these is the same trick at heart: the text and the bytes are not the same thing. Text is one interpretation of bytes. If the program interprets them differently from the way strings does, strings loses.

Which tells you what to do about it. Stop asking what the bytes say and start asking what the program does to them. That is Part 2.

Reading raw bytes with xxd

When you need to stop trusting interpretations and look at the actual thing.

xxd shows a file as bytes. Three columns: where you are, the bytes in hex, and those same bytes as text where they can be.

$ xxd m01_helloghost | head -4

The first four bytes are 7f 45 4c 46. As text that is a control character followed by ELF. That is the magic number: the fingerprint that tells the operating system what kind of file this is. Every ELF starts with it. This is exactly what file looks at.

Jumping to a specific place

You will rarely want the whole file. Use -s to seek and -l to limit:

$ xxd -s 0x2000 -l 64 m04_xorlock

00002010: fc00 0000 0000 0000 0a20 2041 4343 4553  ......... ACCES

Nine bytes, all above 7f, followed by a zero, sitting exactly where a string constant would be. This is the second time this book has shown you those particular bytes and it will not be the last.

When strings finds something and you want to see its surroundings:

$ strings -t x m03_rotgate | grep ZVQ
    3038 ZVQQYRBHG

The first command gives you the offset, the second shows you what is parked around it. Neighbours are informative. Constants that get used together tend to be stored together.

Chapter 10

The decompiler is a translator, not an oracle

The most important attitude adjustment in the book.

The decompiler output looks like source code. It is not source code. It is a guess, produced by a very good program, about what source code could have compiled into these instructions.

Usually the guess is excellent. Sometimes it is wrong. Knowing the difference is most of the skill.

Things the decompiler will do that will confuse you

You seeWhat is actually going on
undefined8, undefined4 "Eight bytes, and I do not know what kind." Not an error, just an admission. You can fix it with Ctrl+L.
0x1a instead of 26 Ghidra defaults to hex for constants. Right-click a number and there is a Convert submenu with decimal, character, and more.
Multiplication turned into shifts and adds The compiler did that, not Ghidra. Chapter 1.
Divisions turned into a magic multiply Same. Dividing by a constant is done by multiplying by a strange large number. This is normal and always looks alarming.
in_EAX, extraout_EDX, unaff_RBX Ghidra got the function signature wrong, usually the argument count. A sign you should fix the signature, not a sign the program is weird.
A whole function collapsing to return; You are looking at a stub, or Ghidra failed to find the real function boundary. Chapter 17.
The habit that separates the good from the stuck

When the decompiler output makes no sense, look at the Listing.

The Listing is not a guess. It is the actual instructions, decoded. If the decompiler says something baffling, put your cursor on that line and look at what it lines up with in the middle panel. Nine times out of ten the assembly is obvious and the decompiler was just being clumsy about types.

You do not need to be fluent in assembly to do this. You need to be able to read about fifteen instructions, and Chapter 11 gives you those fifteen.

The fifteen instructions that cover almost everything

x86-64, the survival subset

Two more facts and you can read the arguments to any call:

  • On x86-64 Linux, the first six arguments go in rdi, rsi, rdx, rcx, r8, r9, in that order.
  • The return value comes back in rax.

So when you see this, you already know it is comparing your buffer against a constant at address 0x4020af:

lea    -0x80(%rbp),%rax     ; address of the local buffer
lea    0xe2f(%rip),%rdx     # 4020af   the other string
mov    %rdx,%rsi            ; second argument
mov    %rax,%rdi            ; first argument
call   4010b0 <strcmp@plt>
test   %eax,%eax            ; was the answer zero?
jne    40129b               ; not equal -> go print ACCESS DENIED
On ARM it looks different and it is the same

If you are on an ARM Chromebook the registers are x0 to x30, arguments go in x0 through x7, the return value is in x0, and the syntax puts the destination first instead of last.

None of that changes the decompiler output, which is where you will be living. The C that Ghidra produces from an ARM binary and from an x86 binary of the same program is nearly identical. That is the whole point of the decompiler and it is why this book teaches it before assembly.

Chapter 11

Your loops, compiled

Lab: lab_flow. Everything you learned in Volume One, from the other side.

Import lab_flow into your project and analyse it. It is not locked. There is nothing to solve. It exists so you can look at eight shapes you already understand and learn what each one looks like coming back the other way.

An if / else

/* what you wrote */
if (n > 10) return 1; else return 0;

/* what Ghidra shows */
undefined8 simple_if(int param_1)
{
  if (param_1 < 0xb) {
    return 0;
  }
  return 1;
}

Two things changed and neither is a problem. 10 became 0xb, because the compiler rewrote "greater than 10" as "less than 11" and Ghidra prints in hex. And the branches swapped order. The behaviour is identical. Get comfortable with this now, because it happens in every single program.

A for loop

int count_for(int param_1)
{
  int local_10;
  int local_c;

  local_10 = 0;
  for (local_c = 0; local_c < param_1; local_c = local_c + 1) {
    local_10 = local_10 + local_c;
  }
  return local_10;
}

Ghidra reconstructs for loops almost perfectly. local_c is the counter, local_10 is the accumulator. Rename them i and total with L and it becomes the source code.

A switch

Look at pick. A switch with a few scattered cases compiles into a chain of comparisons. A switch with many consecutive cases compiles into a jump table: an array of addresses that the program indexes into. Ghidra recognises both and shows you a switch statement either way.

Remember jump tables. Mission 07 is a jump table wearing a disguise.

And the one you came for

int the_infinite_loop(int param_1)
{
  int local_c;

  local_c = param_1;
  while( true ) {
    local_c = local_c * 3 + 1;
    if (0x3e8 < local_c) break;
    if (local_c % 2 == 0) {
      local_c = local_c / 2;
    }
  }
  return local_c;
}

There it is. while(true), which is what for(;;) compiles to, and a break that is the only way out. 0x3e8 is 1000.

In Volume One an infinite loop was a bug that froze your game and you had to learn to spot one before it happened. Here it is a shape you can recognise in machine code that somebody else wrote. Same thing, opposite direction, and you are on the other side of it now.

Chapter 12

Cross-references

The single best move in the tool. Learn this one properly.

During analysis Ghidra built a graph of every place in the program that touches every other place. Which functions call this function. Which instructions read this string. Which code writes to this variable.

That graph is called cross-references, usually shortened to XREFs, and it turns a haystack into a signpost.

The move

Put your cursor on anything at all and press Ctrl+Shift+F. A window lists every place that refers to it. Double-click a row to go there.

Try it on the Mission 01 password. Go to Window → Defined Strings, which lists every string Ghidra found, click NULLYWASHERE, press Ctrl+Shift+F. One reference, inside main, at the strcmp. You have gone from "here is a string" to "here is the exact instruction that decides whether you win" in two keystrokes.

Now go and destroy Mission 02 with it

Import m02_haystack. Open Window → Defined Strings. There are over two thousand.

Do not read them. Go to main in the decompiler instead and read the code. You will find something like this:

for (local_10 = 0; local_10 < 0x7d1; local_10 = local_10 + 1) {
    local_14 = local_14 + (int)*catalogue[local_10];
  }
  printf("Checksum of vault: %d\n",(ulong)(uint)local_14);
  printf("Master password: ");
  ...
  iVar1 = strcmp(local_98,"████████████");

The two thousand strings go through a loop that adds up their first characters and prints a number. Busywork. Only one string reaches the strcmp, and the decompiler puts it right there in the line.

That is the whole lesson. Do not search the data. Read the decision. The data was two thousand items. The decision was one line.

The three questions XREFs answer
  • Who calls this? Put the cursor on a function name. Now you know how you can reach it, and whether anything reaches it at all.
  • Who uses this string? Straight from a string to the logic around it. This is how you start on almost any program: find a message you saw on screen, cross-reference it, and you have landed in the middle of the code that matters.
  • Who touches this variable? Especially useful for globals. Every read and every write, listed.
The universal opening move

For any program, ever, that prints something you can see:

void unscramble(char *param_1,char *param_2)
{
  char cVar1;
  int local_c;

  for (local_c = 0; param_1[local_c] != '\0'; local_c = local_c + 1) {
    cVar1 = param_1[local_c];
    if ((cVar1 < 'A') || ('Z' < cVar1)) {
      param_2[local_c] = cVar1;
    }
    else {
      param_2[local_c] = (char)((int)(cVar1 + -0x41) + 0xd) % 0x1a + 'A';
    }
  }
  param_2[local_c] = '\0';
  return;
}

Read the three numbers

HexDecimalMeaning
0x4165The letter A. Subtracting it turns a letter into a position, 0 to 25.
0xd13How far to move each letter.
0x1a26Letters in the alphabet. This is the wrap-around.

Position, plus thirteen, wrap at twenty-six, back to a letter. That is ROT13, and you met it in Chapter 6.

If you seeSuspect

0x41 / 0x61'A' or 'a'. Letter arithmetic.

Bytes that used to be text

Mission 04, and writing your first decoder.

You have already seen these bytes twice, in Chapters 3 and 7:

strings finds nothing in this program because every one of those bytes is above 0x7f. Open it in Ghidra and read main:

    local_38[local_c] = blob[local_c] ^ 0xa5;
}
local_38[local_c] = '\0';
iVar1 = strcmp(local_98,local_38);

Nine bytes, each XORed with 0xa5, then compared against what you typed.

Why XOR is used for this constantly

XOR compares two bits and gives 1 if they differ. Applied to a byte with a key, it scrambles it. Applied again with the same key, it unscrambles it perfectly. One operation, both directions, no lookup table.

  'W'  = 0x57 = 0101 0111
  key  = 0xa5 = 1010 0101
  XOR         = 1111 0010 = 0xf2   ← the first stored byte

  0xf2 = 1111 0010
  0xa5 = 1010 0101
  XOR  = 0101 0111 = 0x57 = 'W'    ← and back again

It is fast, it is tiny, and it is not encryption. Anyone who reads the code has the key, because the key has to be in the code for the program to work. That is not a flaw in this particular program, it is a fact about all of them: a program that can decode something must contain everything needed to decode it.

Write the decoder

You could do nine XORs by hand. Do not build the habit. Write three lines of Python instead, because Mission 12 has 109 bytes and you will want the muscle memory:

$ python3
>>> blob = [0xF2,0xEA,0xE9,0xE3,0xED,0xE4,0xE9,0xE0,0xFC]
>>> ''.join(chr(b ^ 0xA5) for b in blob)
'?????????'
Getting the bytes out of Ghidra without typing them

Select the bytes in the Listing, right-click, Copy Special → Byte String. You get them as text, ready to paste into Python. For a nine-byte blob it hardly matters. For a hundred-byte one it matters enormously, and typing a hundred hex bytes by hand introduces exactly one typo, every time, guaranteed.

The thing to understand about stripping

Nothing was lost that the program needed. The code is byte-for-byte the same. The only thing removed is a table of human-readable names that the processor never looked at in the first place.

Gillbert, you already know this concept from somewhere else entirely. Tyler puts out a record as Wolf Haley, then as Igor, then as Sir Baudelaire. Same person. Same voice. Different name on the cover, and if you only know how to look up names you are stuck, and if you know how to recognise the work you are not.

A stripped binary is Igor. Same program. No name tag. Learn to recognise the work.

Finding main in a stripped binary

Method 1, the reliable one: follow entry.

Every Linux program starts at a symbol called entry (sometimes _start), which is never stripped because the operating system needs it. It does a little setup and then calls a libc function called __libc_start_main, handing it the address of main as the first argument.

So: double-click entry, look at the decompiler, and find the call:

void entry(void)
{
  __libc_start_main(FUN_004011c9,...);
  do {
                    /* WARNING: Do nothing block with infinite loop */
  } while( true );
}

FUN_004011c9 is main. Click on it, press L, rename it main. Ten seconds, and your table of contents has its first real entry.

Method 2, the fast one: follow a string.

You already know this move from Chapter 12. Run the program, note a message, find it in Defined Strings, cross-reference it. Whatever function you land in is almost always main for a program this size, because the banner gets printed from main.

Method 3, the crude one that works surprisingly often. Sort the function list by size. In a small program, main is usually the biggest thing that is not library boilerplate.

What to do next, every time

  1. Find main and rename it.
  2. Read main top to bottom and rename every function it calls, based on what it obviously does. FUN_00401180 prints a congratulations message? That is win. Do it now.
  3. Rename the locals in main. user_input, expected, result.
  4. Only then start actually solving the puzzle.

That takes five minutes and it will save you thirty. Every time you go back into the project, the names are still there. That is the whole reason Ghidra has projects at all.

Two things that will look broken and are not

"Do nothing block with infinite loop" in entry. Not a bug and not a puzzle. __libc_start_main never returns, and Ghidra does not know that, so it renders the unreachable code after it as a loop. Ignore it.

A function shows as data, or a chunk of code is grey. Ghidra's analysis missed it. Put the cursor at the start, press D to disassemble, then F to make it a function. This is normal and it is why those two keys exist.

Practice before it counts

Strip a binary you already understand and find your way back around it:

$ cp lab_flow lab_flow_stripped
$ strip lab_flow_stripped
$ file lab_flow_stripped

Import it, find main using method 1, then find the_infinite_loop without its name. You know exactly what you are looking for, which makes this a fifteen-minute exercise instead of an hour of confusion later.

Every mission so far had a password sitting somewhere, in some disguise, and the job was to get it out.

Gilfoyle, on licences

Every overpriced enterprise product does exactly this. You type in your name, it does some secret arithmetic to your name, and if the number you paid for matches the number the arithmetic produces, congratulations, you are licensed. Hooli sells this. Everyone sells this. It is the same three lines of code in a forty-thousand-dollar suit.

And it is fundamentally broken, because the machine that checks the licence has to contain the recipe for making licences, or it could not check them. The lock and the key are printed on the same page. Once you can read that page, the number Gavin Belson wants ten thousand dollars for, you can generate all day, for free, for any name, forever.

I am not telling you to go do that. I am telling you why the entire concept is a beautiful, doomed lie, and why writing your first keygen feels less like learning and more like being let in on something.

What you are looking for

The program is stripped, so start with Chapter 17. Find main, rename it, and read it. It calls one small function with the name you passed in and compares the result against the number you passed in. That small function is the whole mission.

It will look roughly like this, and the numbers are the point:

uint FUN_00401180(char *param_1)
{
  char cVar1;
  int local_10;
  uint local_c;

  local_c = 0x1505;
  for (local_10 = 0; param_1[local_10] != '\0'; local_10 = local_10 + 1) {
    cVar1 = param_1[local_10];
    if (('`' < cVar1) && (cVar1 < '{')) {
      cVar1 = cVar1 + -0x20;
    }
    local_c = local_c * 0x21 ^ (int)cVar1;
  }
  return local_c & 0x7fffffff;
}

Translating that into Python, line by line

Ghidra showsWhich means
local_c = 0x1505Start the accumulator at 5381.
'`' < cVar1 && cVar1 < '{'Is this a lowercase letter? (Between a and z.)
cVar1 + -0x20Subtract 32, which turns lowercase into uppercase.
local_c * 0x21 ^ cVar1Multiply by 33, then XOR in the character.
& 0x7fffffffKeep the low 31 bits. Forces the answer positive.
The one thing that will get you

In C, that accumulator is a 32-bit unsigned integer. When you multiply it by 33 and it gets too big, the top bits fall off. It wraps around.

Python integers do not do that. They just get bigger, forever. So a direct translation will give you the wrong answer after about the sixth character and you will have no idea why.

You have to force the wrap yourself, on every step:

acc = (acc * 33) & 0xFFFFFFFF

This is the single most common bug in a first keygen and now it will not be yours.

Chapter 23

gdb: freezing time

Mission 09. Breakpoints, and reading a value the program never stored.

gdb, the GNU Debugger, is the heavy tool. It runs a program under its complete control and lets you freeze it at any instruction, look at any value, change anything, and step forward one instruction at a time. It is how you answer the question static analysis cannot: what is actually in there, right now?

Mission 09 needs it. The response code is not stored anywhere. The program computes it by running a mixer four thousand times, then compares. You could reimplement the mixer, and the walkthrough shows you how. Or you could freeze the program the instant before it checks, and just look.

Gilfoyle, on cold starts

The mission is called Cold Start because that is what Anton does every time the power blinks: it wakes up remembering nothing and has to rebuild its state from scratch, grinding through the same setup work, every time, because it refuses to write anything important to disk where someone could read it. Anton trusts no one. I taught it that.

This program is the same. It will not store its answer where you could find it. It rebuilds it fresh, every run, and holds it for exactly as long as it takes to check. Your entire job is to be standing there, in that one instant, with a breakpoint. Blink and it is gone and it starts over.

The whole technique in six commands

$ gdb ./m09_coldstart

(gdb) run                  # start it; type any guess at the prompt
(gdb) x/s $rsi             # show the second argument as a string
(gdb) x/s $rdi             # and the first, for good measure
(gdb) continue             # let it finish
(gdb) quit

Remember from Chapter 10 that the first two arguments to any function live in rdi and rsi. strcmp(a, b) puts your guess in one and the real answer in the other. x/s $rsi means "examine, as a string, the thing rsi points at." The real response code prints out, computed and sitting in memory, a single instruction before it would have been checked.

The breakpoint that catches the wrong fish

You will see break strcmp suggested everywhere, and on this program it does not work. The loader resolves symbols using strcmp long before your code runs, so it stops there first, then in the vDSO lookups, then in libc. You can continue past them, but there are dozens, and your input has not been typed yet. You will run out of patience before you run out of breakpoints.

Breaking on the address of the program's own PLT stub skips all of that. That stub is only ever reached from your code, never from the loader, so it stops in exactly the right place on the first hit. Find the address with objdump -d m09_coldstart | grep strcmp@plt, or in Ghidra, then break *0xADDRESS. This is the habit worth building.

The program that does not want to be watched

Gilfoyle takes over from here

The first two thirds of this book were about programs that just sat there and let themselves be read. Sweet. Trusting. Dead.

The rest of it is my part, because the rest of it is about programs that fight. A program that notices it is being watched and changes its behaviour is the first genuinely interesting thing in this whole series, and I say that as someone who read all four volumes and felt almost nothing.

Here is the only philosophy you need, and it is also just true about people: anything that decides based on what it can see can be lied to about what it can see. The program asks "am I being watched." You make sure the answer it hears is no. That is the entire discipline. Everything after this is technique.

Run Mission 10 normally and it asks for a passphrase. Run it under gdb and it refuses to play:

$ gdb ./m10_watchdog
(gdb) run
  A DEBUGGER IS ATTACHED. Nully is not doing this with you watching.
  Terminating.

The program can tell it is being debugged. There is a system call named ptrace that a program can use on itself: if the call succeeds, nothing is watching; if it fails, something already has the program under a debugger, because you are only allowed one watcher at a time.

So the check is simple and, in the decompiler, obvious:

lVar1 = ptrace(PTRACE_TRACEME,0,0,0);
if (lVar1 < 0) {
    /* a debugger is attached, bail out */
    return 1;
}

You cannot just extract the passphrase, because like Mission 09 it is computed, never stored. You genuinely need to run it under a debugger, and it genuinely refuses to run under a debugger. So you have to get past the guard. Three ways, in increasing order of how much they teach you.

Way one: lie to it from inside gdb

Let the ptrace call happen, then change its answer before the program can look. Break on ptrace, let it return, overwrite the result in rax with a zero (meaning success, nothing watching), and continue:

$ gdb ./m10_watchdog
(gdb) break ptrace
(gdb) run
(gdb) finish              # let ptrace return
(gdb) set $rax = 0         # overwrite its answer: "nobody here"
(gdb) continue            # now type the passphrase when asked

The program checks a value you just forged and happily carries on, watched the whole time.

Way two: change the jump

The check ends in one conditional jump: "if ptrace failed, go to the bail-out." Flip that single jump and the bail-out becomes unreachable. In the disassembly it is one byte: a jns (jump if not-signed, i.e. if the result was not negative) at address 0x40128d. This is the doorway to the next chapter.

Way three: remove the check entirely

Make the whole detection function return "all clear" no matter what, by overwriting its first instructions. Also next chapter.

This is a real arms race, and this is the shallow end of it

Anti-debugging in real software gets deep. Programs check ptrace in three different ways, time themselves to notice the pauses a debugger causes, look for breakpoint bytes in their own code, and check again ten more times while running. Defeating serious protection is a career.

But every last bit of it is the same move you just made: the program asks a question about its own environment, and you arrange for it to get the answer you want instead of the true one. Once you have done it once, the idea never surprises you again.

Chapter 25

Changing the program itself

Patching. One byte, and the lock is no longer a lock.

Everything so far left the program alone and worked around it. Patching does the opposite: it edits the program's own bytes so it behaves differently forever. This is the most powerful move in the book and, done carelessly, the easiest to get wrong, so we do it carefully.

The idea

A program's decisions come down to conditional jumps. "If the password is wrong, jump to the failure message." If you change that jump, you change the decision. You are not guessing the password. You are editing out the part of the program that cares.

The one-byte patch on Mission 10

From the last chapter, the anti-debug check turns on a single jns instruction at 0x40128d, and the byte for jns is 0x79. The byte for an unconditional jmp of the same length is 0xeb. Change that one byte from 0x79 to 0xeb and the check always takes the "all clear" road, debugger or not.

Here is a tiny Python patcher that does it safely, checking the byte is what we expect before touching it:

import sys

src, dst = "m10_watchdog", "m10_patched"
offset   = 0x40128d - 0x400000   # file offset: load address is 0x400000

data = bytearray(open(src, "rb").read())
assert data[offset] == 0x79, "not the byte I expected, stop"
data[offset] = 0xeb          # jns  ->  jmp
open(dst, "wb").write(data)
print("patched")
$ python3 patch.py
patched
$ chmod +x m10_patched
$ echo "wrongpass" | ./m10_patched
No debugger detected. Good. Passphrase:

The anti-debug message is gone. The program now runs under gdb happily, and you can read the passphrase out of it with no lying required, because you removed the reason for the lie.

Why 0x400000, and how to find any file offset

These missions are built without address randomisation, so the program loads at a fixed address, 0x400000. An instruction Ghidra shows at 0x40128d therefore sits at file offset 0x40128d - 0x400000 = 0x128d.

You do not have to trust that subtraction. In Ghidra, click the byte, right-click, Patch Instruction, and it shows you the exact bytes and can even write the change for you. The Python method is here because it is universal and because doing it by hand once teaches you what "Patch Instruction" is actually doing.

The three rules of patching
  1. Always work on a copy. cp the file first. Every single time. A botched patch turns a program into garbage and you want the original back.
  2. Keep the length the same. Replacing one two-byte instruction with a different two-byte instruction is safe. Making it longer or shorter shoves everything else out of place and breaks the whole file. When you need a different length, pad with 0x90, the "do nothing" instruction, called a nop.
  3. Check before you write. That assert is not decoration. Confirm the byte is what you think it is, so a wrong address fails loudly instead of corrupting something silently.
Optional but excellent: patch Mission 10 the other way

Instead of flipping the jump, neuter the whole detection function so it always returns "all clear". Find where the anti-debug function starts, and overwrite its first three bytes with 0x31 0xc0 0xc3, which is xor eax,eax ; ret, meaning "return zero immediately." Same result, and it teaches you that "make this function return a constant" is a move you have forever now. It is one of the most useful patches in existence.

Gilfoyle, on why this is the good part

Reading a program is polite. Patching a program is not.

You just reached into something somebody built, found the one byte where it makes up its mind, and changed its mind for it. It does not know. It will never know. It will run for the rest of its life believing it made that decision itself, and it is wrong, and you are the reason.

That loop is Son of Anton's processor. The array of bytes is a program written for it. Nully is the program.

That array of bytes is a program. And the loop reading it is a tiny computer, built inside this program, that runs it. This is called a bytecode virtual machine, and it is the real technique that the toughest commercial software protection is built on.

What you are looking at

switch(prog[pc]) {
case 0x11:  acc = input[prog[pc+1]];        break;  // LOAD a character
case 0x20:  acc = acc ^ prog[pc+1];           break;  // XOR
case 0x21:  acc = acc + prog[pc+1];           break;  // ADD
case 0x22:  acc = acc - prog[pc+1];           break;  // SUBTRACT
case 0x23:  acc = rotate(acc, prog[pc+1]);    break;  // ROTATE
case 0x30:  if (acc != prog[pc+1]) fail = 1;   break;  // CHECK
case 0xff:  // HALT
}

That switch is a processor. Six instructions, an accumulator, a program counter. It is the smallest possible version of the exact thing your real CPU does, and once you have written down what each opcode means, you can read the 109-byte program the same way Ghidra let you read x86.

How to actually solve it

You have two honest routes and both are legitimate.

Route A: be the disassembler. Write down the meaning of each opcode. Then walk through the 109 bytes by hand, or with a short Python script, and work out for each character what value it must have started as to survive its chain of operations and pass its CHECK. This is genuinely satisfying and it is what the walkthrough does in full.

Route B: solve it one character at a time. Notice that each character is handled independently, loaded, transformed, checked, before the next one starts. So you can find the twelve characters one at a time instead of all at once. That is a foothold that turns an impossible-looking wall into twelve small steps.

Why this is the right final boss

A VM defeats every quick trick in this book at once. strings sees a blob of data. ltrace sees no interesting library calls, because the comparison is done by hand inside the loop. The decompiler shows you the interpreter but not the meaning of the program it interprets. You cannot copy an answer out because the answer was never a value, it was a computation described in a language you had to learn first.

The only thing that beats it is understanding, all the way down. Which is the thing this entire book was quietly building toward. If you can read this one, you can read almost anything, because almost everything harder is just this with more opcodes.

Why setInterval, and not a real forever-loop

You might think: a timer is a loop, so I will write while (true) and count down inside it. Do not. That is the Volume One infinite loop, the bad one, and in a browser it does not tick, it freezes. The page locks solid and nothing paints, because your loop never lets go long enough for the screen to update.

setInterval(tick, 1000) is the fix. It says "run tick once, then go away and let the page breathe, then come back in 1000 milliseconds and do it again." It is a loop that takes turns instead of hogging. Same idea as while (true), house-trained. That single difference is a genuinely important thing to understand about how browsers work, and you just met it.

Make it yours

Once it works, it is yours to mess with. Some ideas, in rising order of showing off:

  • Make it flash or shake when it drops under 10.
  • Add a text box so you can type the abort code into your own clock, and have it stop and say DEFUSED.
  • Make it count in tenths of a second instead of whole seconds. What number do you change? (Yes, it is the 1000.)
  • Give it sound. A tick every second. A very bad noise at zero.

This is the same move as Volume One: build the thing, get it working, then make it do something the instructions never asked for. That is the whole game.
